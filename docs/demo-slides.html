What is OPR?

OPR = One Patient Record

One Patient. One record.

However many Resources and Devices touch it.

Resource: an ambulance unit, vehicle and crew.  Device: the tablet it works on.

  • In a real emergency a patient is often handled by more than one Resource: one picks them up, another takes over for the long drive, a third may meet them at a hospital.
  • Each Resource works on its own Device. Without a shared record, each Device holds its own piece of the story.
  • We use the glossary words from CONTEXT.md on every slide: Resource, Device, Incident, Transfer leg.
The problem

Without OPR, the story breaks at every Handover

  • Left: today's risk. Each Device holds its own piece; the next Resource starts from what someone tells them out loud.
  • Right: every Resource reads and writes the same Patient. A Resource that takes over sees everything at once.
What an OPR means

Four promises

1

Same Patient everywhere

Every Resource sees the same Patient.

2

Nothing overwritten by accident

Every change from every Device is kept.

3

Takeover sees everything

A Resource that takes over gets the whole picture at once.

4

Network drops are survivable

A short loss of network loses no entry.

  • These four promises are what the live demo will prove, one scenario at a time.
  • Promise 4 is the one people usually doubt; scenario 5 pulls the plug on purpose.
What Mini OPR is

A demo, not a product

×No product code
×No real data
×No real integrations

It shows, on one laptop, how an OPR should behave when one Patient travels across several Transfer legs, each handled by a different Resource on its own Device.

All Patient data is fictional.
  • Mini OPR exists to make the behaviour visible and testable, not to be shipped.
  • It is deliberately small: three seeded Resources (Alpha 1, Bravo 2, Charlie 3), one Coordinator, an EOC page.
  • Nothing is deployed; it runs with npm run dev.
One vocabulary

The words we use

EOC

Creates Incidents and the first Transfer leg. Changes nothing after that.

Incident

One emergency, with exactly one Patient and its Transfer legs.

Patient

The person being transported. Shared by all Transfer legs.

Transfer leg

One Resource's part in an Incident. Active, then Completed for good.

Resource

An ambulance unit: vehicle and crew.

Join / Handover

A Resource attaches itself to an Incident by pasting its id.

Device

The tablet a Resource works on. Here: one browser tab.

Event

One recorded change to a Patient, or the completion of a Transfer leg.

Event log

The numbered Events written on one Device, in order.

Offset

How far into a Device's Event log the Coordinator has stored, without gaps.

Coordinator

The single place where every Device's Event log is gathered.

Coordinator epoch

One lifetime of the Coordinator's data, from a Reset to the next.

  • We agreed these words before any code was written. They live in CONTEXT.md, with synonyms to avoid (for example "trip" or "hop" for Transfer leg, "server" for Coordinator).
  • Tickets, code and UI all use exactly these words. That alone removed a lot of confusion for people and for AI agents.
Architecture

The pieces

  • EOC creates an Incident and the first Transfer leg. It changes nothing after that. It writes over HTTP and reads over a read-only /watch socket.
  • Device: one Resource in one browser tab. It edits the Patient, Joins Incidents and completes its own Transfer leg. Its Event log lives in localStorage.
  • Coordinator stores every Event, rebuilds the Patient with the same reducer the Device uses (applyEvent), and pushes new Events to every Device of the Incident in realtime.
  • Coordinator page shows one lane per Device with its Offset, the merged log, and the Reset button.
What Mini OPR solves

Five hard questions

Where does the truth live?
In the Events. Each Device writes its own Event log; the Coordinator gathers them and rebuilds the Patient.
Two Devices edit one field?
Newest edit wins, field by field. Vitals and notes are always kept.
The network drops?
Save on the Device first, send in the background, resume from the Offset.
A new Resource takes over?
It Joins by Incident id and gets everything at once. No accept step.
When is the Incident over?
Closed while it has no Active leg. A Join reopens it.
  • These are the questions any real OPR must answer. The next four slides show how, then we run it live.
  • After a Handover the earlier Resource can still edit the Patient: there is no "owner".
Two Devices edit at once

Newest edit wins, field by field. Lists keep everything.

Same result in any arrival order, checked with property tests over every permutation.

  • Name, date of birth and triage: the newest edit wins, per field. On a tie in time, the larger eventId wins, so every Device decides the same way.
  • Vitals and notes are append only: never overwritten, sorted by time.
  • No conflict marks, no settle entries, no conflict dialog. Device and Coordinator share one pure reducer, so there is one implementation to test.
  • The "any order" claim is tested with fast-check property tests that fold every permutation of a set of Events.
The network drops

The Offset: stored without gaps

Upload

Everything above my Offset.

Download

A full snapshot after each connect, then realtime pushes.

Result

Nothing lost, nothing sent twice.

  • Each Device numbers its own Events: seq 1, 2, 3. The Coordinator remembers, per Device, how far it has stored without gaps. That number is the Offset.
  • The Device saves every change on itself first and sends it in the background. After reconnect it resends only what is above the Offset.
  • The Coordinator page shows each Device's Offset live, so you can watch it move during the demo.
For the developers

Sync, step by step

  • One plain WebSocket per Device (ADR 0001). The first message is always hello with the Device's epoch (ADR 0004).
  • The Coordinator answers with its epoch and the Offset for this Device, then a full snapshot of what the Device can see. The Device dedups by eventId.
  • Push: insert, applyEvent and bump the Offset in one SQLite transaction, then ack. Then fan out to every other Device of the Incident (ADR 0005, 0006).
  • Reconnect backoff: 0.5, 1, 2, 4, then at most 5 seconds. Ping every 5 seconds.
When is it over?

Transfer legs end for good. Incidents can reopen.

  • A Transfer leg is Active from creation until a Device of its Resource completes it with a legCompleted Event. Then it is Completed for good.
  • An Incident is Closed while it has no Active leg. While Closed, Devices lock the Patient form, but the Coordinator still stores every Event.
  • A Join opens a new Transfer leg, so the Incident is Active again. Scenario 6 shows exactly this.

Scenario 5 of 7

Short network drop

TerminalAlpha 1Bravo 2
  1. Stop the Coordinator process (Ctrl+C).
  2. Every Device shows offline. Keep editing on Alpha 1: new Events wait in "My Event log".
  3. Start the Coordinator again. Devices reconnect by themselves.
  4. Waiting Events are sent from the Offset, stored, and reach Bravo 2.
Point outNothing lost, nothing sent twice. A plain restart keeps the Coordinator epoch, so Devices keep their data.
  • Ctrl+C on the terminal, or kill the Coordinator part of npm run dev.
  • Reconnect backoff: 0.5, 1, 2, 4, then at most 5 seconds. Be patient for a few seconds.
  • There is no pending count on the offline indicator, by design. Point at "My Event log" instead.
Scenario 6 of 7

Complete legs, Incident Closed, Join reopens

Alpha 1Bravo 2Charlie 3
  1. Alpha 1: "Complete my leg" (confirm; cannot be undone).
  2. Alpha 1 can still edit: Bravo 2's Transfer leg is still Active.
  3. Bravo 2 completes its Transfer leg: the Incident is Closed, both composers lock.
  4. Charlie 3 Joins the same id: the Incident reopens.
Point outAn Incident is Closed while it has no Active leg. A Join reopens it.
  • After step 1 the feed shows a system line for the completed Transfer leg.
  • While Closed, Devices lock the Patient form, but the Coordinator still stores every Event.
  • Closed is derived from the Transfer legs, never stored.
Scenario 7 of 7

Reset

Coordinator pageAll DevicesEOC page
  1. Coordinator page: Reset (with a confirm).
  2. A new Coordinator epoch appears.
  3. Every Device disconnects, sees the new epoch on reconnect, and clears itself.
  4. EOC and Coordinator pages show the empty state, no reload.
Point outThe Coordinator epoch tells a Device its local data belongs to a Coordinator that no longer exists.
  • Compare with scenario 5: a plain restart keeps the epoch, so Devices keep and resend their data. A Reset changes the epoch, so Devices clear themselves instead of bringing old Events back.
  • The Device keeps its deviceId; its Event log starts again at seq 1.

The process

Shape, decide, build

1. Shape the language

  • domain-modeling skill
  • CONTEXT.md glossary, with words to avoid

2. Decide, one question per ticket

  • Wayfinder map: issue #1
  • research: transport, SQLite
  • grilling: schema, legs, identity, sync, tables, channels, tests
  • prototype: screen layout
  • Result: ADRs 0001 to 0008

3. Build in vertical slices

  • Spec #15: 74 user stories
  • 12 tickets, ready-for-agent, with blocked-by links
  • AI agents implement in parallel worktrees
  • Resolution comment + commit on main
Working demo: 115 tests, CI green
  • Shape: agree on words before code. Decide: every technical choice is a GitHub ticket with a written resolution and an ADR. Build: thin end-to-end slices that agents can pick up on their own.
  • CONTEXT.md was updated inline as decisions sharpened the language.

Agentic build

12 slices, explicit blockers, agents in parallel

Arrow: "blocks". Any unblocked ticket could be picked by an agent at the same time as others.

  • The spec was cut into 12 thin vertical slices. GitHub's native "blocked by" links make the order explicit.
  • Three tickets had no blockers (#16, #25, #26), so three agents could start at once.

Lessons

What made it work

1

Decide before you build

Agents built against decisions, not guesses.

2

One vocabulary

Glossary loaded into every session through CLAUDE.md.

3

Small, independent slices

End to end, testable alone, explicit blockers.

4

Tests prove the hard claims

Property tests, real SQLite in memory, real socket.

5

Humans own the decisions

People answered the questions; agents did the work.

  • 1: every technical choice was a ticket with a written resolution and an ADR.
  • 2: tickets, code and UI all say "Transfer leg", never "trip" or "hop".
  • 3: explicit blockers let agents run in parallel without stepping on each other.
  • 4: "same result in any order" is checked with fast-check property tests; storage tests run on real SQLite in memory; the sync protocol is tested over a real socket.
  • 5: people answered the grilling questions and chose between prototype variants.

Wrap-up

Three things to remember

1

Events are the record

Every Device's Event log, gathered by one Coordinator, rebuilt the same way everywhere.

2

Local first, then sync

The Offset makes a network drop a non-event: nothing lost, nothing twice.

3

Decide, then let agents build

Clear words, written decisions, small slices: AI agents built it in one morning.

  • Close the loop with the four promises from the start: same Patient everywhere, nothing overwritten, takeover sees everything, network drops survivable.
